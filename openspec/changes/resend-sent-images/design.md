# Design

## Context

送信キューは、件（`jobs`）と件の画像（`job_files`）を SQLite に記録する。再送は
`ModalityService.retry` が送信失敗の件だけを受け、`unsent_files` の画像を同じ件で
送る。件を送信中にする条件付きの更新は、待機中と送信失敗の件だけを対象にする
（同じ件を2つの処理が同時に送らないため。spec 12 の 8.2）。

## Goals / Non-Goals

**Goals:**

- 送信完了の件も、何回でも送り直せるようにする
- 撮影の画面から、送信の結果の後に送り直せるようにする

**Non-Goals:**

- 送り直すときに送信先を選ぶこと（別の送信先へは CLI の `send <フォルダ> --to` で
  送れる）
- 送り直しのときに画像を作り直すこと
- 相手の側の重複の扱い（同じ SOP Instance UID の2回目を上書きするか、断るか）を
  DTG で決めること。相手の応答の Status をそのまま記録する

## Decisions

1. **送信完了の件の送り直しは、新しい件にする。** 送信完了の件を送信中に戻すと、
   その件の保管確認の結果と送信の時刻が上書きされ、履歴が分からなくなる。新しい
   件にすれば、件ごとに送信と保管確認の結果が残る。CLI の `send <フォルダ>` が今
   すでに新しい件を作っているのと同じ形になる。
   採用しなかった案：送信完了の件を送信中に戻して全部を送り直す（履歴が消える）
2. **送信失敗の件は今のまま。** 送れていない画像だけを同じ件で送る（今の決まり）
3. **送信中の判定は今のまま。** 新しい件は待機中から送信中にするので、同じ件を
   2つの処理が同時に送らない決まりは崩れない。送信完了の件の送り直しを2回続けて
   押せば、件が2つできる（どちらも送る）。画面は押した後に応答が返るまでボタンを
   押せなくする
4. **送る前の検証は今のまま。** 新しい件も、送る前にシンボリックリンクとフォルダの
   外のファイルを断る（spec 12 の 8.2）。撮影の後にフォルダのファイルが消えていたら、
   送れずに理由を知らせる

## Risks / Trade-offs

- [相手が同じ SOP Instance UID の2回目を Warning や Failure で返す] → 相手の Status を
  記録して表示する。Failure なら送信失敗になり、理由に Status が出る
- [送信キューの件が増える] → 件は今も消さない（画像のファイルも消さない）。履歴の
  量はテストの道具として問題にならない
