# Design

## Context

動機は proposal.md の Why のとおり。今の `Dockerfile` は、リポジトリの設定の例
（`config/app_config.yaml`。Web 画面は `127.0.0.1` で待ち受ける）をそのままイメージに
入れているので、コンテナの外から Web 画面に届けるには、`bind_address` を `0.0.0.0` に
した設定ファイルを利用者が作ってマウントする必要がある。書き込むフォルダは uid 10001
（`dtg`）の所有で、ホストのフォルダをマウントするときは、そのフォルダを uid 10001 が
書き込める形にする必要がある。

## Goals / Non-Goals

**Goals:**

- イメージを取得して1行で Web 画面を起動でき、1行でファイルを作成できる
- タグの push のときだけ GHCR に公開する workflow を用意する

**Non-Goals:**

- この change でタグを push して公開すること（承認の後に別に行う）
- 古いイメージを自動で削除すること（下の Risks のとおり、今は要らない）
- arm64 のイメージ

## Decisions

1. **イメージの中の設定ファイルを、ビルドのときに `web.bind_address: "0.0.0.0"` に
   書き換える。** リポジトリの設定の例は `127.0.0.1` のまま残す（Python の環境で
   動かすときの既定は変えない）。書き換えは CI と同じ awk の1行で、`web:` の節だけを
   対象にし、書き換えられたことを grep で確かめてビルドを失敗させる。
   採用しなかった案：環境変数で待ち受けのアドレスを変えられるようにする（コードの
   変更が要り、設定する場所が2つになる）・コンテナ用の設定ファイルを別に置く（設定の
   例が2つになり、片方が古くなる）
2. **パスワードの必須は変えない。** `0.0.0.0` で待ち受けるとパスワードのファイルが
   必須になる今の動作（spec/12a の 10.9）により、パスワード無しでは起動しない
3. **書き込むフォルダは `1777`（誰でも書き込め、他人のファイルは消せない）にする。**
   `--user "$(id -u):$(id -g)"` で動かすと、マウントした出力フォルダのファイルが
   ホストの利用者のものになり、ホスト側で権限を変える手順が要らない。`--user` を
   指定しないときは、今と同じ uid 10001 で動く
4. **公開の workflow は `on: push: tags: ['v*']` だけで動かす。** 権限は
   `contents: read` と `packages: write` だけにする。actions は commit の SHA で固定する
   （checkout は ci.yml と同じ SHA。docker/setup-buildx-action v4.4.1・login-action
   v4.6.0・metadata-action v6.2.0・build-push-action v7.4.0）。タグは metadata-action の
   `type=semver,pattern={{version}}` と、版のタグのときに付く `latest` にする。
   `org.opencontainers.image.source` のラベルで、パッケージをこのリポジトリに結び付ける
5. **ADR-0023 を作成する。** 配布の主な形をイメージにすることと、公開の条件を残す

## Risks / Trade-offs

- [README の `docker pull` は、最初のタグの push まで失敗する] → usage.md に、
  公開の前は `docker build` でイメージを作る手順を残す
- [`1777` のフォルダは、同じコンテナの中の別の利用者からも書き込める] → コンテナは
  1つの用途だけで動かし、ほかの利用者のプロセスは無い。sticky bit で他人の
  ファイルは消せない
- [古いイメージが GHCR に残り続ける] → 版ごとのタグは消さずに残す方針で、
  `latest` を付け替えたときにタグの無いイメージが残るだけ。公開の頻度が低いので、
  今は削除の仕組みを作らない。増えたら GHCR の画面か `gh api` で消す
