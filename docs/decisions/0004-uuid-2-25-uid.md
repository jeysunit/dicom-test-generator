# ADR-0004: UUID 2.25 UID

- 状態：採用
- 作成日：2026-02-22
- 最終更新日：2026-10-22

## 背景

DICOM UIDの生成方式を決定する必要がある。

### 要求

- グローバルに一意なUIDが必要
- DICOM Standard準拠
- 簡単に実装可能

### 選択肢

1. **UUID 2.25方式**: `2.25.{UUID整数値}`
2. **組織OID方式**: IHE Japanから組織OIDを取得し、`1.2.392.xxx.{枝番}`
3. **ハードコードUID**: 固定UID + 連番

### 現状

- 組織OIDを持っていない
- 個人開発プロジェクト
- テストデータ生成が目的

## 決定

デフォルトでUUID 2.25方式を採用する。

ただし、将来的に組織OIDを取得した場合に切り替え可能な設計とする。

### 実装方針

```python
class UIDGenerator:
    def __init__(
        self,
        method: Literal["uuid_2_25", "custom_root"] = "uuid_2_25",
        custom_root: str = ""
    ):
        self.method = method
        self.custom_root = custom_root
        self.counter = 1
    
    def generate_study_uid(self) -> str:
        if self.method == "uuid_2_25":
            return f"2.25.{uuid.uuid4().int}"
        elif self.method == "custom_root":
            uid = f"{self.custom_root}.{self.counter}"
            self.counter += 1
            return uid
```

### 設定ファイル

```yaml
# config.yaml
uid:
  method: "uuid_2_25"  # デフォルト
  custom_root: ""
```

組織OID取得後：

```yaml
uid:
  method: "custom_root"
  custom_root: "1.2.3.4.5"  # 架空の例。自分の組織に割り当てられた根を使う
```

## 影響

### 良い点

- ✅ 組織OID不要で即座に開発開始可能
- ✅ グローバルに一意性が保証される
- ✅ DICOM Standard準拠（RFC 3061）
- ✅ 実装が簡単（uuid.uuid4()のみ）
- ✅ 衝突リスクがほぼゼロ

### 悪い点

- ⚠️ UIDが長い（約40文字）
  - 例: `2.25.113059749145936325402354257176981405696`
  - **影響**: DICOMビューアでは問題なし、表示が若干長い程度

### リスクと軽減策

- ⚠️ **将来的にカスタムRootに切り替えた場合、過去データとの互換性がない**
  - 軽減策: Study Instance UIDが変わるため、別スタディとして扱われる（問題なし）
- ⚠️ **連番カウンタの管理が必要（カスタムRoot使用時）**
  - 軽減策: Phase 1で永続化機能を追加

### トレードオフ

- UUID 2.25: 長いが実装簡単、組織OID不要
- カスタムRoot: 短く読みやすいが、組織OID取得が必要

## 実装

### Phase 0

- UUID 2.25方式のみ実装
- カスタムRoot対応は設計のみ

### Phase 1以降

- カスタムRoot方式を実装
- 連番カウンタの永続化

## 改訂（2026-10-21）：カスタムRoot の一意を生成ごとの番号で守る

連番カウンタは永続化しなかったため、生成のたびに 1 に戻り、同じ
`custom_root` で 2 回生成すると Study・Series・SOP Instance UID が
前の生成と同じになった。UID は世界で一意でなければならない（PS3.5 9）。

- 決定：連番カウンタを永続化せず、ルートの後ろに生成ごとの番号（64 ビットの
  乱数）を連結する（`{root}.{run_id}.{counter}`）。状態のファイルを
  持たないので、保存先を削除しても、コンテナを作り直しても同じ方法で動作する。
  一意性は確率による（2.25 の UUID と同じ考え方）。2 回の生成で番号が
  一致する確率は 2^-64 で、無視できる
- ルートの形式を PS3.5 9.1 で検証する（成分の先頭の 0 を拒否する・64 文字まで）。
  番号と連番を連結しても 64 文字に収まるよう、ルートは 35 文字まで
- 例のルート `1.2.392.200036.9999` は、他の組織の登録されたルートの下にあるように
  見えるため、架空の `1.2.3.4.5` に替えた
- 詳しい形は [spec/02_core_engine.md](../spec/02_core_engine.md) の
  UIDGenerator と [spec/06_dicom_rules.md](../spec/06_dicom_rules.md)
