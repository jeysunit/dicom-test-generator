# ADR-0014: 通常の経路は規格どおりに生成し、規格の違反は異常のデータの経路で定めたものだけを生成する

- 状態：採用
- 日付：2026-10-21
- 作成日：2026-10-22

## 背景

DTG は、DICOM と HL7 の規格に違反しないことを開発の前提にしている。一方で、
受信側のシステムが不正なデータにどう反応するかをテストするために、あえて規格に
違反したデータ（異常のデータ）を生成する機能を持つ。

前提をそのまま全体に適用すると、異常のデータの機能が成り立たない。逆に、異常の
データがあるからといって前提を緩めると、通常の画像にも違反が混入する。そうなると、
テストで見つかった問題が受信側の不具合なのか、DTG の不具合なのかを区別できない。

## 決定

1. **生成を「通常の経路」と「異常のデータの経路」に分け、規格に違反しないという
   前提は通常の経路にだけ適用する。** 通常の経路は、`abnormal.level` が `none`
   で、`abnormal.allow_invalid_sop_uid` を使わない生成。異常のデータの経路は、
   `abnormal.level` が `mild`・`moderate`・`severe` のときと、
   `abnormal.allow_invalid_sop_uid` を使うとき
2. 通常の経路では、規格に合う値だけを受け付け、合わない値は生成の前に拒否する。
   Job・テンプレート・装置プロファイル・予約・画面と CLI の入力のどれから来た値も
   同じ扱いにする。生成する画像は規格どおりにする
3. 異常のデータの経路で生成する違反は、定めた壊し方だけにする。定義は
   [spec/02](../spec/02_core_engine.md) の AbnormalGenerator にある（壊すタグの表、
   Pixel Data の削除、SOP Instance UID の 0 始まり）。定義に無い違反は、異常の
   データの経路でも生成しない。生成できるようにするときは、先に定義に追加する
4. 異常のデータは、組み立てた Dataset に最後に適用する。通常の経路のチェック
   （Type 1 の属性、画素値の範囲、DS の長さ、UID の形式、文字コード、入力の `\`）
   は、適用前の値か、定義に無い入力にかかる。そのため、通常の経路のチェックが
   定義済みの壊し方を妨げることはない

## 検討した選択肢

- **前提を全体に適用し、異常のデータの機能を削除する**：受信側の耐性をテストする
  という用途が無くなるので採用しない
- **異常のデータの経路では何を生成してもよいことにする**：何が壊れるかを利用者が
  予測できず、テストの期待値を書けない。通常の経路にチェックを追加するたびに、
  異常のデータで生成できるものが知らないうちに変わる。どちらも避けたいので採用
  しない

## 結果

- 通常の経路の画像に違反があれば、DTG の不具合として修正できる
- 異常のデータで生成できる違反は spec/02 の表で確認できる。テストの期待値を
  書きやすい
- 定義に無い違反（例：廃止された Transfer Syntax）を生成したくなったら、spec/02 の
  定義を広げる変更として扱う。知らないうちに生成できるようにはしない
