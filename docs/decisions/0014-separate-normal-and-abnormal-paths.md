# ADR-0014: ふつうの経路は規格どおりに作り、規格の違反は異常のデータの経路で約束したものだけを作る

- 状態：採用
- 日付：2026-10-21
- 作成日：2026-10-22

## 背景

このツールは、DICOM と HL7 の規格に違反しないことを開発の前提にしている。
一方で、受け取る側のシステムが壊れたデータにどう振る舞うかを試すために、
あえて規格に違反したデータ（異常のデータ）を作る機能を持つ。

前提をそのまま全体に掛けると、異常のデータの機能が成り立たない。逆に、
異常のデータがあるからといって前提を緩めると、ふつうに作った画像にも
違反が紛れ込み、試験の結果が受け取る側の不具合なのか、このツールの誤りなのかを
区別できなくなる。

## 決定

1. **生成を「ふつうの経路」と「異常のデータの経路」に分け、規格に違反しない
   前提はふつうの経路にだけ掛ける。** ふつうの経路は、`abnormal.level` が
   `none` で、`abnormal.allow_invalid_sop_uid` を使わない生成。異常のデータの
   経路は、`abnormal.level` が `mild`・`moderate`・`severe` のときと、
   `abnormal.allow_invalid_sop_uid` を使うとき
2. **ふつうの経路は、規格に合う値だけを受け、合わない値は生成の前に断る。**
   Job・テンプレート・装置のプロファイル・予約・画面と CLI の入力のどれから
   来た値も同じ。作る画像は規格どおりにする
3. **異常のデータの経路が作る違反は、約束した壊し方だけにする。** 約束は
   [spec/02](../spec/02_core_engine.md) の AbnormalGenerator にある
   （壊すタグの表、Pixel Data の削除、SOP Instance UID の 0 始まり）。
   約束に無い違反は、異常のデータの経路でも作らない。作れるようにするときは、
   先に約束に足す
4. **異常のデータは、組み終えた Dataset に最後に当てる。** ふつうの経路の
   確かめ（Type 1 の属性、画素の範囲、DS の長さ、UID の形、文字コード、
   入力の `\`）は、その前の値か、約束に無い入力に掛かる。そのため、
   ふつうの経路の確かめが約束の壊し方を狭めることはない

## 検討した選択肢

- **前提を全体に掛け、異常のデータの機能を外す**：受け取る側の耐性を試す
  という用途が無くなるので採らない
- **異常のデータの経路では何を作ってもよいことにする**：何が壊れるかを
  利用者が予測できず、試験の期待値を書けない。ふつうの経路の確かめを足すたびに、
  異常のデータで作れるものが黙って変わる。どちらも避けたいので採らない

## 結果

- ふつうの経路の画像に違反があれば、このツールの誤りとして直せる
- 異常のデータで作れる違反は spec/02 の表で読める。試験の期待値を書きやすい
- 約束に無い違反（例：廃止の Transfer Syntax）を作りたくなったら、spec/02 の
  約束を広げる変更として扱う。黙って作れるようにはしない
