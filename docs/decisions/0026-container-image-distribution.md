# ADR-0026: Docker のイメージを主な配布の形にし、タグの push と手動のときに GHCR に公開する

- 状態：採用
- 作成日：2026-10-23
- 最終更新日：2026-10-24

## 背景

DTG を使うには、Python の環境を作るか、`Dockerfile` から自分でイメージをビルドする
必要があった。イメージの中の設定は Web 画面を `127.0.0.1` で待ち受けるので、
コンテナの外から Web 画面を開くには、設定ファイルを作ってマウントする必要もあった。
テストの相手（PACS・RIS）をコンテナで動かす利用者が多く、公開したイメージを取得して
すぐに動かせる形が求められていた。

## 決定

1. 主な配布の形を Docker のイメージにする。README のクイックスタートと usage.md は
   Docker から始め、Python の環境での起動は開発する人向けに development.md に置く
2. イメージは `ghcr.io/jeysunit/dicom-test-generator` に、`v` で始まるタグの push と、
   手動の実行（`workflow_dispatch`）のときだけ公開する
   （`.github/workflows/publish.yml`）。公開できるのは `v1.2.0` の形
   （`v` と 3 つの数）のタグだけで、タグの push も手動の実行も、ほかの ref と形では
   最初のステップで失敗する。タグは版と `latest`。`main` への push と PR では
   公開しない。公開はタグを push する人か、手動で実行する人が決める操作にする
3. イメージの中の設定は、Web 画面を `0.0.0.0` で待ち受ける形にする。`0.0.0.0` では
   パスワードのファイルが必須なので（spec/12a の 10.9）、パスワード無しでは起動しない
4. 書き込むフォルダ（`logs`・`modality_state`・`output`）は `1777` にし、
   `--user "$(id -u):$(id -g)"` で動かせるようにする。マウントした出力フォルダの
   ファイルがホストの利用者のものになる
5. 公開の workflow の権限は `contents: read` と `packages: write` だけにし、actions は
   commit の SHA で固定する

## 検討した選択肢

- **`main` への push のたびに公開する**：PR をマージするたびに `latest` が変わり、
  利用者が取得するイメージがいつの版か分からなくなる
- **環境変数で待ち受けのアドレスを変えられるようにする**：コードの変更が要り、
  待ち受けのアドレスを設定する場所が、設定ファイルと環境変数の2つになる
- **コンテナ用の設定ファイルを別に置く**：設定の例が2つになり、片方が古くなる。
  ビルドのときにリポジトリの設定の例から作る形にした

## 結果

- イメージを取得すれば、パスワードのファイルを1つ作るだけで Web 画面を起動できる
- 最初の公開（タグの push）までは、README の `docker pull` は失敗する。usage.md に
  `docker build` の手順を残す
- 公開の頻度が低いので、古いイメージを削除する仕組みは作らない。版のタグは残し、
  `latest` を付け替えたときにタグの無いイメージが残るだけ
