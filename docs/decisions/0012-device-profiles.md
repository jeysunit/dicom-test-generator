# ADR-0012: 装置のプロファイルで装置の出し方を擬態する（仕組みは公開・写しは非公開）

## ステータス

**Accepted** - 2026-10-20（2026-10-18 に承認者が案 A を選んだ。実装は済んで
いる：`app/core/device_profile.py`・`app/services/profile_loader.py`・
`profiles list`・`--profile`）

## 背景

もとのモダリティのテンプレートは、実在の装置のコンフォーマンス
ステートメント（DICOM PS3.2）を読み、その装置の DICOM の出し方を
擬態するためのものだった。テンプレートの名前と中身に実在の製品の名前が
入っていた。

spec/12b の 17 章（公開のテンプレートに商用の製品の名前を使わない）を
採った PR（#5）で、そのテンプレートを架空の名前の `ct_generic` に替え、
spec/06 からコンフォーマンスステートメントの行を外した。このとき
テンプレートの目的（装置の擬態）を確かめておらず、擬態の仕組みそのものが
消えた（誤り）。

### 要求

- 特定の装置が出す形の DICOM を、本物の装置なしで作れる
- 公開のリポジトリに、実在の製品の名前・実在の装置の写しを置かない
- 写した元（どの文書のどの版か）を記録できる
- 写し方の手順が文書になっている（人が替わっても写せる）

## 決定

1. **案 A：擬態の仕組みは公開し、実在の装置の写し（プロファイル）は
   公開しない。** 仕様は
   [spec/13_device_profiles.md](../spec/13_device_profiles.md)
2. **プロファイルはモダリティのテンプレートの上に重ねる（置き換えない）。**
   順は Job → テンプレート → プロファイル → 病院テンプレート。装置の値
   （製造者・型名・ソフトウェアの版・装置の番号・Implementation Version
   Name・SOP Class）は病院テンプレートでも変えない
3. **実在の装置のプロファイルは外のフォルダ（`DTG_PROFILE_DIRS`・
   `profiles.search_paths`）から読む。** リポジトリの `profiles/` には
   架空の例（`profiles/examples/`）だけを置き、`.gitignore` と試験で
   ほかの物が入らないようにする
4. **同じ名前のプロファイルが2か所以上にあれば誤りにする。** 上の置き場が
   黙って下を隠さない
5. **知らない欄・合わない値（モダリティ・転送の形・文字コード）は
   誤りにする。** 黙って直さない・無視しない
6. **古い名前のテンプレートを読みに来たら、プロファイルの置き場へ
   案内する誤りにする**（古い名前はいまと同じく SHA-256 で持つ）

### 理由

#### 1. 案 A を選ぶ理由

| 案 | 中身 | 良い点 | 悪い点 |
|----|------|--------|--------|
| **A. 仕組みは公開・写しは非公開（採った）** | 仕組み・例は公開、実在の装置の写しは外の置き場 | 仕組みを公開で試験・レビューできる。製品の名前が公開に出ない | 写しの置き場を利用者が持つ |
| B. 写しも公開 | もとのテンプレートの形に戻す | 手間が少ない | 実在の製品の出力と誤解されうる。spec/12b の 17 章と合わない |
| C. 仕組みごと非公開 | 擬態の機能を外の道具にする | 公開の側は単純 | 仕組みの試験・レビューが公開でできない。二重の保守 |

#### 2. 重ねる理由（置き換えない理由）

- コンフォーマンスステートメントに書いてあるのは属性の出し方で、撮影の
  値（kVp・スライス厚・窓）は書いていない。撮影の値はテンプレートが持つ
- 1つのテンプレートに複数の装置を重ねられる
- 置き換えにすると、テンプレートの欄の写し忘れが黙って既定の値になる

#### 3. 同じ名前を誤りにする理由

- 先に見つかった方を使うと、例のプロファイルと非公開のプロファイルの
  どちらで作ったかが、出力を見ても分からない
- 名前を変えれば済むので、誤りにしても困らない

#### 4. 装置の値を病院テンプレートで変えない理由

- 施設の設定で変わるのは施設の名前・Station Name・文字コードで、装置の
  製造者・型名・ソフトウェアの版は変わらない
- いまの病院テンプレートの重ね方は浅い（`general_equipment` を丸ごと
  替える）ので、プロファイルの値を病院の前に置くと黙って消える

## 影響

### 良い点

- 装置の擬態の仕組みが戻る
- 写した元（`source`）がプロファイルに残る
- 公開の側に実在の製品の名前を書かずに済む

### 悪い点

- 実在の装置のプロファイルは、利用者が非公開の場所で持ち、写しを保守する
- P1 で効くのは装置の値・転送の形・文字コード・属性・プライベートタグ
  まで。UID の形・画素・シリーズの並び（P2）、ワークリスト（3a）、
  MPPS・保管の確認（3c）は後の段
  - 追記（2026-10-20）：MPPS・保管の確認（`services.mpps`・
    `services.storage_commitment`）は実装済み。UID の形・画素・シリーズの
    並び（P2）とワークリストの欄は未実装（spec/13 の 11 章）

### リスク

- 非公開のプロファイルを誤って公開の側に置く
  - **軽減策**：`.gitignore` で `profiles/` の下を例以外すべて外す。
    試験で、リポジトリに例しか無いことを確かめる
- 写した値の誤り（文書の読み違い）
  - **軽減策**：写す手順（spec/13 の 5 章）と、作った画像を文書の表と
    並べて確かめる手順を文書にする
